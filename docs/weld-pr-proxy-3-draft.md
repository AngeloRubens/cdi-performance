**Title:** WELD-XXXX Array based per-thread interception context stack

## Summary

`InterceptionDecorationContext.Stack` wrapped an `ArrayDeque`. Every invocation of a method of an intercepted
subclass pushes and pops the subclass handler, and every client proxy invocation made inside an interception
context pushes and pops a `NULL_INSTANCE` marker. With `ArrayDeque` each of those costs ring-buffer index arithmetic
(`dec`/`inc` with wrap-around), the `head == tail` growth check, the `elementAt` null check of `pollFirst` and two
extra `isEmpty()` calls in the wrapper.

The stack is now a plain `CombinedInterceptorAndDecoratorStackMethodHandler[]` plus a `size` index:

- `startIfNotOnTop(context)`: `size == 0` → push; otherwise compare `elements[size - 1]` and push if different;
- `push`: store, increment, grow (`Arrays.copyOf`, doubling) only when full; the empty → non-empty transition still
  makes the thread-local holder reference the stack strongly;
- `pop`/`end`: read the top, clear the slot (no handler or bean instance is retained), decrement; the non-empty →
  empty transition still drops the strong reference (the idle stack stays only weakly reachable from the
  thread-local, so an idle thread never retains a Weld class);
- `peek()` returns `null` when empty, as `ArrayDeque.peekFirst()` did.

No generated bytecode changes, no public API change, no behaviour change:

| aspect | before | after |
|---|---|---|
| self-invocation suppression (top == handler) | top of the deque | `elements[size - 1]` |
| `NULL_INSTANCE` marker pushed by client proxies | `addFirst` | `push` |
| nested / recursive calls, decorators | unbounded deque | unbounded array (grows by doubling) |
| exception paths | generated `try/catch` calls `Stack.end()` | unchanged |
| `null` element | `NullPointerException` (deque) | `NullPointerException` (explicit check, now *before* the holder is touched) |
| `Stack.end()` on an empty stack | `NoSuchElementException` | `NoSuchElementException` |
| static `peek()` / `endInterceptorContext()` with no active stack | `EmptyStackException` | unchanged |
| `toString()` | `Stack [elements=[top, ..., bottom]]` | same format |
| class loader leak protection (weak holder) | yes | unchanged |

A unit test (`InterceptionDecorationContextTest`) covers push/pop order, `NULL_INSTANCE`, growth beyond the initial
capacity, the empty-stack exceptions and reuse of the idle stack.

## Considered and not done

- **Passing the stack from the client proxy to the intercepted subclass** (to save the second
  `ThreadLocal.get()`): there is no channel between the two generated classes except the method arguments and
  per-thread state. The subclass method is the bean's public method and is also invoked directly (self
  invocation, `@Dependent` injection, decorators, reflection), so it cannot assume that a caller looked the stack
  up. A per-handler cache of "the stack of the last thread" is racy or, when made safe, causes cache-line
  ping-pong between threads calling the same `@ApplicationScoped` bean; `ScopedValue` is not available on the
  minimum JDK. A real solution needs a second generated entry point, see below.
- **Observation for a follow-up** (not implemented): only the *top* of the stack is ever inspected
  (`isDisabledHandler`, `AroundInvokeInvocationContext.create`, `startIfNotOnTop`). When a client proxy call
  reaches a *non-intercepted* method of an intercepted subclass whose handler is set, the subclass always ends up
  with its own handler on top, so the `NULL_INSTANCE` marker pushed by the client proxy is unobservable; the
  client proxy could skip `startIfNotEmpty()` (one `ThreadLocal.get()` and one push/pop) for those methods. This
  requires the client proxy factory to know exactly which methods the subclass factory treats as intercepted
  (interceptors *and* decorators, bridge/default/private methods) and to handle the "handler not yet set"
  construction case, so it is left for a separate change.
